# Probe result — plugin content is not reachable

**`RESULT=PLUGIN_CONTENT_NOT_REACHABLE`**, with the positive control passing, so
the negative is trustworthy.

```text
[control] /Game/_Dawnwalker/Inventory/Items/ITM_Weapon_SwordGreatMaster1a
  beforeLoad=present   loadAsset=ok   afterLoad=present

[probe]   /ForgeRegistryProbe/M_ForgeRegistryProbe0001
  beforeLoad=absent    loadAsset=ok   afterLoad=absent
```

The control goes present → present, proving the method works. The probe stays
absent after an explicit load, so **the game cannot resolve the plugin's content
at all.**

Note `loadAsset=ok` on the probe is not a success signal — the call did not throw,
but produced no object. A silent null, which is why the before/after comparison
matters rather than the call's own return.

## What this actually establishes

**The plugin at `Dawnwalker\Mods\ForgeRegistryProbe\` is never mounted.** Nothing
in the installed setup mounts `.uplugin` folders from that path:

- UE4SS's `BPModLoaderMod` loads blueprint mods from `Content\Paks\LogicMods`, not
  uplugins from `Dawnwalker\Mods`.
- The `uplugin` and `Mods/` strings found in the shipped exe were weak evidence —
  they show engine plugin support is compiled in, not that the game scans that
  directory for mods. That inference was too generous and this result corrects it.

**It does not disprove "mounting appends the registry."** We never got as far as
mounting, so that question is still open — just unreachable by this path.

## Where that leaves the goal

For a genuinely new inventory item, content has to arrive by a route that *is*
proven to mount here — an IoStore container in `Content\Paks\~mods`, which is how
every working mod on this install loads — and the item still has to be in an asset
registry to be discovered.

Which puts it back on **the `AssetRegistry.bin` override**, the route parked in
`REGISTRY-OVERRIDE-PROGRESS-2026-09-12.md`. The next milestone there is unchanged:
a byte-exact round trip of the 5,426,463-byte registry before anything modified
goes near the game.

Two things this exercise did leave behind that are worth keeping:

- `assetregistry.py` now parses two independent registries byte-exactly (40,908
  names shipped, 1,105 names cooked), so the format work is real progress toward
  that round trip.
- A cook **does** emit a registry naming plugin assets, in the same three-name
  shape items use. If a mount route is ever found, the content side is ready.

## Cost of the four restarts, recorded honestly

Three of the four were my bugs, all caught by the probe's own diagnostics rather
than by guessing:

1. Bound to F10, which `ForgeItemLoadProbe` and `ConsoleEnabler` already use.
2. A Windows path in a Lua literal — `\s` is not a valid escape, so the whole
   script failed to load and the keybind did nothing.
3. `LoadAsset` and the registry calls need the **game thread**; without
   `ExecuteInGameThread` they throw "can only be called from within the game".

The positive control earned its place: run three reported the probe asset missing
*and* the control missing, which would have read as a clean negative. Without the
control I would have concluded the route was dead and gone off to rewrite a 5.4 MB
registry on the strength of a broken query.
