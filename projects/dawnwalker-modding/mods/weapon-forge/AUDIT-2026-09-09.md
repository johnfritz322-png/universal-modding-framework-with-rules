# DawnwalkerWeaponForge — independent audit, 2026-09-09

Audit of Codex's `DawnwalkerWeaponForge-VerifiedBuild` by Claude, using this
repository's own `games/blood-of-the-dawnwalker/tools/utoc.py` plus the new
`verify_container.py` in this folder.

**Verdict: do not install this archive.** Three blockers, one of them actively
harmful to the game install. None of this is a criticism of the safety posture —
Codex refused to install it and said so plainly, which was the right call. The
problems are in what the cook actually produced.

## What checked out

File integrity is honest. All three files match the SHA-256 values Codex
documented, byte for byte:

| File | Documented hash | Result |
| --- | --- | --- |
| `DawnwalkerWeaponForge-Windows.pak` | `B7382DCD…54AD` | MATCH |
| `DawnwalkerWeaponForge-Windows.ucas` | `30971CD0…42DE` | MATCH |
| `DawnwalkerWeaponForge-Windows.utoc` | `DCC8697B…98F3D` | MATCH |

Container shape is also correct for a Dawnwalker mod: TOC v8, flags `0x09`
(Compressed | Indexed, **not** encrypted), mount point `../../../`. That matches
the shipped-mod pattern recorded in `games/blood-of-the-dawnwalker/DAWNWALKER_RULES.md`.
The "432 cooked packages" claim is real — 432 `ExportBundleData` chunks.

## Blocker 1 — the cook swept in 390 packages of stock engine content

Of 445 named files in the container, **392 are stock Unreal Engine content** —
`Engine/Content/EngineMaterials`, `Engine/Plugins/Animation/ControlRig`,
`Engine/Plugins/Interchange`, `Engine/Content/MobileResources`, and so on. Only 53
are weapon assets, and those 53 are **duplicated across two mount paths**:

```
DawnwalkerWeaponForge/Content/Weapons/...
DawnwalkerWeaponForge/Plugins/DawnwalkerWeaponForge/Content/Weapons/...
```

so the real unique payload is ~25 assets. The other 132 MB is engine cook.

### Why that matters, stated carefully

IoStore resolves packages by chunk ID, and chunk IDs sit in the TOC in the clear —
no AES key needed. Intersecting the mod's chunk-ID table with the base game's:

```
base chunks : 778,650
mod chunks  :     948
colliding   :     390   (379 ExportBundleData + 11 BulkData)
```

**Collision is not itself a fault.** It is the override mechanism every replacement
mod uses. Measured on this same install with `verify_container.py`:

| Container | Colliding chunks | Meaning |
| --- | --- | --- |
| `SkillsNoTimeCost` | 112 of 113 (99.1%) | working as designed — it replaces trait assets |
| `DualSenseAtlas` | 4 of 5 (80.0%) | working as designed — it replaces button icons |
| `DawnwalkerWeaponForge` | **390 of 948 (41.1%)** | **all accidental** |

The difference is intent. WeaponForge adds five new swords; it replaces nothing on
purpose, so its correct collision count is **zero**. Every one of those 390 is an
engine asset the cook picked up by accident, and because `~mods` loads after the
base container, those stock UE 5.5 copies would win over Dawnwalker's own cooked
engine content.

Whether that visibly breaks the game was not tested — it would be reckless to test
it on a real install, and the point is that nobody should have to. An additive mod
has no business shipping `EngineMaterials` at all.

This also corrects the build README, which describes a bad install as loading "an
inert package". Inert would be harmless. This would take effect.

**Fix:** cook only `/DawnwalkerWeaponForge/Weapons` with engine content excluded.
The result should be tens of files, not 445, and must report **0 collisions** under
`verify_container.py --expect-none` before anyone installs it. Also drop
`WeaponForgePreview.umap` — a test map should not ship — and pick one mount path
rather than shipping plugin and project copies of every asset.

## Blocker 2 — the swords are placeholder boxes

Every source mesh in
`D:\Dawnwalker-Modding\Projects\DawnwalkerWeaponForge\SourceArt\Weapons`:

| Mesh | Verts | Faces | Normals | UVs |
| --- | ---: | ---: | ---: | ---: |
| `SM_EmberveilSaber.obj` | 40 | 30 | 0 | 0 |
| `SM_MoonrendCleaver.obj` | 48 | 36 | 0 | 0 |
| `SM_NightfallColossus.obj` | 40 | 30 | 0 | 0 |
| `SM_OathlightLongsword.obj` | 40 | 30 | 0 | 0 |
| `SM_RiftforgedSlabblade.obj` | 40 | 30 | 0 | 0 |

40 verts / 30 faces is five axis-aligned boxes stacked end to end — the raw OBJ is
literally `v -10 -2.8 26` style rectangles. **Zero UVs** means no texture can map
correctly; **zero normals** means nothing shades smoothly. These are blockouts.

Codex's handoff does say "do not claim they are final AAA-quality visuals without
further refinement", which is honest. The gap is bigger than that phrasing suggests:
there is no silhouette, bevel, taper, fuller or crossguard geometry to refine.

**Fix:** these need actual modelling with UVs before any visual work is meaningful.
Worth deciding first whether custom geometry is the goal at all, given Blocker 3.

## Blocker 3 — nothing connects a mesh to an equipped weapon

Correctly identified and left unsolved in the handoff. The content mounts under a
plugin path the shipped game never reads, so even a clean archive displays nothing
until a verified appearance/attachment route exists for this build. Codex declined
to guess it, which was right.

Updated 2026-09-09 18:43 local. **Structure is unchanged** — TOC v8, flags `0x0b`,

Two consequences:

- Codex's `Grant-Dawnwalker-*.ps1` helpers pin exe SHA `7AD7D096…` and will now
  **refuse to run**. That is the safety check working as designed. Update the pin
  deliberately; do not bypass the check.
- Both usmap dumps on disk (`Downloads\Dawnwalker.usmap`, 2026-09-02, and the
  `.rar`, a 2026-09-03 dump) predate the patch, so FModel mappings must be
  re-checked against 258042 before any property names are trusted.

The base container's encryption GUID is still all-zero/default, so the AES key
probably still works — but "probably" is not verified. FModel actually loading is
the proof.
